# IC-20260823-090 阶段三：捏合松手抖动的真机逐帧分析

> 本文件是 IC-090 v2 卡阶段三的交付，回答 `self-check.md` 第十四节里保留给 Lynn 的「场景 C 录制」一项。**本阶段不改产品代码**，只做数据分析与归因。

## 一、结论（先行）

1. **任务卡与上游对「抖动」的几何假设被实测推翻（①已验证事实）。** 松手后**整段 2.36 秒、149 个逐帧样本**里，`presentationFrame`、`contentOffset`、`contentSize`、`zoomScale` 的逐帧差分**全部精确为 0.000000**；`presentationZoomScale` 只有一次 +0.00067 的收敛步。**500 ms 窗口内不存在任何 > 1 pt 的跳变，也不存在任何 > 0.001 pt 的跳变。** 画面几何在松手瞬间就完全静止，没有回弹、没有吸附、没有往返。
2. **真正在松手时刻发生变化的是显示的图像本身（①已验证事实）。** 松手后 **+10.71 ms** 当前张的图像被替换为 PhotoKit 的 **90×120 px 降级预览**，**+74.88 ms** 才被替换回 **3060×4080 px 最终图**。这 **64.17 ms**（60 Hz 下约 4 帧）里，一张 90×120 的缩略图被拉伸到屏幕上 3060×4080 设备像素的显示区域，**线性放大约 34 倍**。
3. **归因（③合理推测）**：Lynn 看到的「松手停下时抖动一下」是这次**图像清晰度的骤降与恢复**，不是几何位移。整条因果链的每一环都有①级证据（第四节），只有「这一现象即 Lynn 所述的抖动」这一步是③。
4. **修复触及未定项 8（图像加载态与请求策略），按 `CLAUDE.md` 第七节停下报告，不自行定案。** 相关两个出厂值 `scaleChangeRequestPolicy = .pinchEnded` 与 `degradedPreviewPolicy = .display` 均登记为 `decided / effective`，改动属产品决策。第六节给出候选方向与代价，供技术负责人与 Lynn 裁定。
5. **验证方式已就绪且不需要新包**：两个策略参数在调试标定面板里都是可切换的 Picker，用 IC-090 阶段二这个包即可做 A/B 复录（第五节）。

## 四、真正发生的事：图像被换成 90×120 缩略图 64 ms

### 1. 实测事件序列（①已验证事实）

| t (ms) | 事件 | 关键数据 |
|---|---|---|
| +0.00 | `scrollViewDidEndZooming` | `scale=2.536828`、`endedAtMinimum=false`、`pinchWasActive=true` |
| +0.26 | `finishNativePinch` | `targetScale=2.536828`、**`path=noWrite`** —— 松手路径不做任何几何写入 |
| +8.96 | `updateUIView` | `写入照片几何=false` |
| **+10.71** | **`图片替换`** | `result=degradedPreview`、**`pixel=(w=90, h=120)`** |
| +16.33 → +74.51 | 逐帧 5 个样本 | `imageRequestResult=degradedPreview`，几何全部不变 |
| **+74.88** | **`图片替换`** | `result=finalImage`、**`pixel=(w=3060, h=4080)`** |
| +91.20 起 | 逐帧样本 | `imageRequestResult=finalImage`，几何仍然不变 |

**降级预览的在屏时长 = 74.88 − 10.71 = 64.17 ms**，60 Hz 下约 3.85 帧。

### 2. 放大倍数（①已验证事实，由实测数字直接算得）

照片层模型尺寸 402×536 pt，缩放后在屏占 402 × 2.536828 = 1019.6 pt 宽，@3x 即 **3059.9 ≈ 3060 设备像素**——与松手后请求并最终拿到的 `3060×4080` 完全吻合（这同时反证了请求目标尺寸的算法：`402 × 3 × 2.536828 = 3060`、`536 × 3 × 2.536828 = 4080`）。

那么这 64 ms 里屏幕上显示的是：**90×120 的位图被拉到 3060×4080 设备像素**，线性放大 **34.0 倍**，面积放大 **1156 倍**。

作为对照，捏合前当前张显示的是 `scale = 1` 时请求的图（目标 402×3 = 1206 px 宽）。所以松手瞬间的观感序列是：

> 略软（1206 px 源拉到 3060，2.54×） → **极糊（90 px 源拉到 3060，34×，持续 64 ms）** → 锐利（3060 px 源，1:1）

中间这一步是一次幅度极大、时长约 4 帧的清晰度塌陷与恢复。

### 3. 因果链（每一环的证据等级）

| 环节 | 内容 | 证据 |
|---|---|---|
| 1 | 松手 → `S2StateMachine` 在 `scaleChangePolicy == .pinchEnded` 时执行 `imageRequestAssetID = currentAssetID; imageRequestRevision += 1` | ① 源码 `S2StateMachine.swift`（`finishNativePinch` 收口处与 `requestImageAfterScaleSettled()`） |
| 2 | `S2View` 把 `machine.imageRequestRevision` 作为 `requestRevision` 传给当前张的图像视图 | ① 源码 `S2View.swift:583` |
| 3 | `.onChange(of: requestRevision)` → 触发器 `.pinchEnded` → `S2ImageRequestDecision.shouldRequest` 在 `scaleChangePolicy == .pinchEnded` 下返回 `true` → 发起新请求 | ① 源码 `S2TemporaryPhotoImageStrategy.swift:178`、`S2Calibration.swift:1181` |
| 4 | 请求用 `deliveryMode = .opportunistic` + `resizeMode = .fast`，PhotoKit 先回调一张最廉价的缓存缩略图（本次为 90×120），再回调最终图 | ① 源码 `S2TemporaryPhotoImageStrategy.swift:74–75`；① 实测两次 `图片替换` 的 `pixel` 与间隔 |
| 5 | `S2ImageRequestDecision.shouldDisplay(isDegraded:strategy:)` = `!isDegraded \|\| degradedPreviewPolicy == .display`；出厂值 `degradedPreviewPolicy = .display`，故**降级预览被允许覆盖已经显示着的图** | ① 源码 `S2Calibration.swift:1195` 与出厂值 `S2Calibration.swift:187` |
| 6 | 屏幕上出现 64 ms 的 34× 放大糊图，随后恢复 | ① 实测（本节第 1、2 小节） |
| 7 | **这一现象即 Lynn 所述的「松手停下时抖动一下」** | **③ 合理推测** |

第 7 环之所以只能是③：诊断埋点记录的是图像替换事件与几何数值，不记录 Lynn 的主观观感；「抖动」这个词本身也可能指位移。但几何侧已被①级证据排除到 0.000000，而图像侧恰好在松手后 10.7 ms 出现一次幅度极大、时长约 4 帧的可见变化，时间与描述（「松手停下时」「一下」）都对得上。

### 4. 已被实测排除的候选原因（均为①）

| 候选 | 排除依据 |
|---|---|
| 吸附归位写入 | 松手后 50 条 `吸附归位写入` 事件，**含 `true` 的 0 条**——`contentInset` / `contentSize` / `contentOffset` / `照片几何` 四个标志全程 false，一次实际写入都没有 |
| `setZoomScale(animated:)` 回弹 | **整段录制 `setZoomScale` 事件数 = 0** |
| `finishNativePinch` 里的归位分支 | `path=noWrite`（①，事件 details 原文） |
| 缩放橡皮筋 / 惯性 | 松手后全部样本 `isZoomBouncing=false`、`isDecelerating=false`、`pagingIsDecelerating=false` |
| 隐式动画把呈现层带偏 | **整段录制 237 个样本的 `animationKeys` 全部为 `[]`**——照片层上没有挂过任何动画，呈现层不可能在无模型写入的情况下自行移动 |
| 外层分页位移 | `pagingContentOffsetX` 全程 8862.000000 不变 |
| 翻页 / 当前张切换 | `currentIndex=21`、`settledIndex=21` 全程不变 |

前两条尤其重要：模型量（`zoomScale`、`contentOffset`、`contentSize`）只能被写入改变，而松手后**一次写入都没有发生**。所以「模型量在两次采样之间跳出去又跳回来」这种可能被事件记录本身排除，不依赖采样率。

## 五、验证方式（把第 7 环由③提升为①）

**都不需要新包**——`scaleChangeRequestPolicy` 与 `degradedPreviewPolicy` 在调试标定面板里都是可切换的 Picker（`S2View.swift:1007`、`:1019`），用 IC-090 阶段二 CI #156 这个包即可。

1. **A/B 复录（首选，最直接）**：在标定面板把 `degradedPreviewPolicy` 切到 `finalImageOnly`，重做一次场景 C（放大约 3 倍 → 松手 → 等 1 秒 → 导出）。
   - 预期：导出里松手后只剩一次 `图片替换 → finalImage`，没有 `degradedPreview` 那一次；几何数值应与本次完全一致（本来就没动）。
   - **若此时 Lynn 主观上不再觉得抖 → 第 7 环成立，归因坐实为①。**
   - 若仍然觉得抖 → 归因被推翻，需要另找原因；届时应优先怀疑本探针覆盖不到的层（见第七节第 1 条）。
2. **反向确认**：把 `scaleChangeRequestPolicy` 切到 `everyScaleChange` 复录。预期图像替换会散布在整个捏合过程中而不是集中在松手后，若「抖动」随之从「松手一下」变成「捏合全程发糊」，则第 1、3 环得到独立印证。
3. **高帧率录屏对时**：240 fps 录屏，与探针时间轴对齐，直接看 t₀+10.7 ms 到 t₀+74.9 ms 这 64 ms 的画面。可给出与主观描述无关的客观证据。
4. **补埋点（若前三条仍不足）**：把「当前显示图像的像素尺寸」加进逐帧字段（目前只在离散事件里有），这样清晰度塌陷会直接出现在逐帧流里，不必跨事件与逐帧两张表对读。**这属探针增强，需要新卡授权。**

## 六、修复方向与代价（不定案，供裁定）

**按 `CLAUDE.md` 第七节，未定项 8「图像加载态与请求策略」不得由执行端自行定案；本卡亦明令「不改产品」。以下只列方向与代价。**

需要说明的是：`scaleChangeRequestPolicy` 与 `degradedPreviewPolicy` 两个参数在登记表里是 `decided / effective`，不是 `placeholder`。也就是说当前行为是**按已定案参数正常工作的结果**，不是实现层的疏漏——要改就是改定案，属产品决策。

| 方向 | 做法 | 代价 / 风险 |
|---|---|---|
| A | `degradedPreviewPolicy` 出厂值改为 `finalImageOnly` | 最小改动（改出厂值，不改逻辑）。但降级预览在**首次加载**时也不再显示，首次进入或翻页到未缓存的照片会从占位背景直接跳到最终图，可能把问题从「松手发糊」搬到「首次加载空窗更长」 |
| B | 只在「当前没有可显示图像」时才允许降级预览覆盖 | 精确命中本问题：已经有图时不降级，没图时仍有快速预览。需要改 `shouldDisplay` 的判定语义（现在只看 `isDegraded` 与策略，不看当前显示状态），属逻辑变更 |
| C | 只在降级图的像素尺寸**不低于**当前显示图时才替换 | 比 B 更严格，能同时挡住「高分辨率请求返回了更低分辨率结果」这一类替换。需要在视图层记住当前显示图的像素尺寸 |
| D | 保持行为，改为交叉淡入 | 不消除清晰度塌陷，只是让它不那么突兀；且引入动画即触及未定项里的动画时长 |
